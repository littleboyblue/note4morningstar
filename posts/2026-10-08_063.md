# 从零搭建：Cloudflare Workers + D1 的 Serverless 后端架构

> 想给一个小应用配后端，传统做法是买台 VPS、装 Nginx、配数据库、管证书、盯着监控——成本不低，维护更累。Cloudflare Workers + D1 提供了另一条路：代码跑在全球边缘节点上，数据库是托管的分布式 SQLite，免费额度对个人项目来说几乎等于不要钱。这个博客的访问统计就是这么跑的。这篇文章从零走一遍完整流程：建项目、配 D1、写迁移、实现 CRUD API、本地调试、部署上线，最后聊聊 D1 的特性和坑。

## 一、为什么是 Workers + D1

先说清楚这套组合解决了什么问题。

**Cloudflare Workers** 是基于 V8 Isolate 的 Serverless 计算平台。和传统容器/虚拟机冷启动几百毫秒到几秒不同，Isolate 的冷启动在毫秒级以内，且代码自动部署到 Cloudflare 全球 300 多个节点，用户请求由最近的节点处理。你不需要关心机器、扩缩容和地域分布。

**D1** 是 Cloudflare 的托管数据库，底层是 SQLite。它通过绑定（binding）直接注入到 Worker 的运行环境里，查询不需要走公网，就是一次函数调用。D1 自动处理备份和只读副本，你面对的是熟悉的关系模型和 SQL，而不是 KV 那种"什么都得自己序列化"的原始接口。

两者组合起来，你可以用**零服务器、零运维**的方式获得一个"边缘 API + 关系数据库"的完整后端，非常适合：

- 个人项目和小型 SaaS 的后端 API；
- 博客/文档站的动态功能（评论、统计、订阅）；
- 内部工具、Webhook 接收服务、定时任务；
- 读多写少、数据量在 GB 级以内的应用。

![Cloudflare Workers + D1 整体架构](images/post-063/architecture.svg)

整体架构如上图：客户端请求打到最近的边缘节点，Worker 在 V8 Isolate 里执行业务逻辑，通过绑定访问 D1；写入路由到 D1 主库，读取可以由就近的只读副本承担。除此之外，同一个 Worker 还可以绑定 KV（缓存）、R2（对象存储）、Queues（异步队列）等服务，按需组合。

## 二、创建项目

Cloudflare 官方脚手架是 C3（`create-cloudflare`）：

```bash
npm create cloudflare@latest my-api -- --type=hello-world --ts
cd my-api
```

脚手架会问几个问题（是否部署、是否用 Git），完成后你会得到一个 TypeScript Worker 项目。核心文件就两个：

- `src/index.ts`：Worker 入口；
- `wrangler.toml`：配置文件，声明名称、入口、兼容性日期和各种绑定。

本地起开发服务器：

```bash
npx wrangler dev
```

默认监听 `http://localhost:8787`，改代码热重载。Wrangler 会在本地用 WorkerD 运行时模拟线上环境，D1、KV、R2 都有本地实现，调试体验和线上一致。

## 三、创建 D1 数据库并绑定

用 Wrangler 创建数据库：

```bash
npx wrangler d1 create my-db
```

输出里会给出 `database_name`、`database_id`。把它们填进 `wrangler.toml`：

```toml
name = "my-api"
main = "src/index.ts"
compatibility_date = "2025-09-01"

[[d1_databases]]
binding = "DB"                # 代码里通过 env.DB 访问
database_name = "my-db"
database_id = "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"
migrations_dir = "migrations" # 迁移文件目录
```

`binding = "DB"` 是关键：它声明了一个注入到 Worker 环境变量里的对象名。之后代码里所有的 SQL 都通过 `env.DB` 发出。

## 四、Schema 与迁移管理

D1 用**迁移文件**管理表结构，约定是 `migrations/` 目录下按文件名顺序执行的 SQL 文件。建第一张表：

```bash
mkdir migrations
```

```sql
-- migrations/0001_create_notes.sql
CREATE TABLE IF NOT EXISTS notes (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL,
  content TEXT NOT NULL DEFAULT '',
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX IF NOT EXISTS idx_notes_created_at ON notes(created_at DESC);
```

本地应用迁移（作用于 wrangler dev 的本地库）：

```bash
npx wrangler d1 migrations apply my-db --local
```

线上应用迁移（先别急着跑，等部署时一起做）：

```bash
npx wrangler d1 migrations apply my-db --remote
```

这套流程的好处是**本地和线上走同一份迁移文件、同一条命令**，不会出现"本地改了表、线上忘了同步"的经典事故。想知道哪些迁移已执行，可以用 `npx wrangler d1 migrations list my-db` 查看。

## 五、实现一个 CRUD API

现在写 Worker 代码。一个不带框架的、结构清晰的 CRUD 实现：

```typescript
// src/index.ts
export interface Env {
  DB: D1Database;
}

const corsHeaders = {
  'Access-Control-Allow-Origin': 'https://your-site.com',
  'Access-Control-Allow-Methods': 'GET, POST, PUT, DELETE, OPTIONS',
  'Access-Control-Allow-Headers': 'Content-Type',
};

function json(data: unknown, status = 200): Response {
  return new Response(JSON.stringify(data), {
    status,
    headers: { 'Content-Type': 'application/json', ...corsHeaders },
  });
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    if (request.method === 'OPTIONS') {
      return new Response(null, { headers: corsHeaders });
    }

    const url = new URL(request.url);
    const parts = url.pathname.split('/').filter(Boolean); // ['notes', '1']

    try {
      // GET /notes —— 列表
      if (request.method === 'GET' && parts.length === 1 && parts[0] === 'notes') {
        const { results } = await env.DB.prepare(
          'SELECT * FROM notes ORDER BY created_at DESC LIMIT 50'
        ).all();
        return json({ notes: results });
      }

      // POST /notes —— 新建
      if (request.method === 'POST' && parts.length === 1 && parts[0] === 'notes') {
        const body = await request.json<{ title?: string; content?: string }>();
        if (!body.title || body.title.length > 200) {
          return json({ error: 'title is required and must be <= 200 chars' }, 400);
        }
        const result = await env.DB.prepare(
          'INSERT INTO notes (title, content) VALUES (?, ?) RETURNING *'
        )
          .bind(body.title, body.content ?? '')
          .first();
        return json({ note: result }, 201);
      }

      // PUT /notes/:id —— 更新
      if (request.method === 'PUT' && parts[0] === 'notes' && parts[1]) {
        const body = await request.json<{ title?: string; content?: string }>();
        const result = await env.DB.prepare(
          `UPDATE notes
             SET title = COALESCE(?, title),
                 content = COALESCE(?, content),
                 updated_at = datetime('now')
           WHERE id = ?
           RETURNING *`
        )
          .bind(body.title ?? null, body.content ?? null, Number(parts[1]))
          .first();
        if (!result) return json({ error: 'not found' }, 404);
        return json({ note: result });
      }

      // DELETE /notes/:id —— 删除
      if (request.method === 'DELETE' && parts[0] === 'notes' && parts[1]) {
        const { meta } = await env.DB.prepare('DELETE FROM notes WHERE id = ?')
          .bind(Number(parts[1]))
          .run();
        if (meta.changes === 0) return json({ error: 'not found' }, 404);
        return json({ deleted: true });
      }

      return json({ error: 'not found' }, 404);
    } catch (err) {
      console.error(err);
      return json({ error: 'internal error' }, 500);
    }
  },
};
```

这段代码体现了 D1 编程模型的几个要点：

1. **永远用 prepared statement + bind**。`prepare('... WHERE id = ?').bind(id)` 让参数走绑定而不是字符串拼接，从根上杜绝 SQL 注入。
2. **三种执行方式各司其职**：`.all()` 返回多行结果；`.first()` 返回单行（或 null）；`.run()` 用于不返回数据的写操作，通过 `meta.changes` 判断影响行数。
3. **`RETURNING *` 很好用**。SQLite 支持 INSERT/UPDATE 后直接返回该行，省掉一次回查。
4. **入口就做好输入校验**。Worker 是你唯一的后端，没有别的防线。

如果路由变多，可以引入 [Hono](https://hono.dev)——一个为边缘运行时设计的轻量框架，API 风格类似 Express，和 Workers/D1 配合得很好：

```typescript
import { Hono } from 'hono';

const app = new Hono<{ Bindings: Env }>();

app.get('/notes', async (c) => {
  const { results } = await c.env.DB.prepare(
    'SELECT * FROM notes ORDER BY created_at DESC LIMIT 50'
  ).all();
  return c.json({ notes: results });
});

export default app;
```

## 六、本地调试

`wrangler dev` 默认使用**本地模拟的 D1**（数据存在 `.wrangler/state` 目录里），迁移用 `--local` 应用。日常开发用本地库，不污染线上数据。

如果想直接连线上数据库调试（慎用），可以加 `--remote`：

```bash
npx wrangler dev --remote
```

还可以用 `wrangler d1 execute` 直接对数据库跑任意 SQL，排查数据问题很方便：

```bash
npx wrangler d1 execute my-db --local  --command "SELECT COUNT(*) FROM notes"
npx wrangler d1 execute my-db --remote --command "SELECT COUNT(*) FROM notes"
```

## 七、部署上线

一条命令：

```bash
npx wrangler deploy
```

部署完成后会拿到 `https://my-api.<your-subdomain>.workers.dev` 的地址。记得上线后应用线上迁移：

```bash
npx wrangler d1 migrations apply my-db --remote
```

建议把这两步固化到 CI 里：push 到 main 后自动 `wrangler deploy && wrangler d1 migrations apply --remote`。这个博客的统计 Worker 就是 GitHub Actions 自动部署的，前端通过 `fetch` 调用 Worker 暴露的 `/track` 和 `/stats` 接口，Worker 里做 Origin 校验后写入存储——模式和本文完全一致。

绑定自定义域名也很简单：在 Cloudflare Dashboard 的 Workers Routes 里把 `api.example.com/*` 路由到这个 Worker 即可，证书自动签发。

## 八、D1 的特性与坑

用 D1 之前，有几件事必须知道：

### 1. 写入有"地理位置"

D1 的主库在创建时会落在一个区域。所有写入都要路由到主库执行，**如果你的用户离主库远，写入延迟会明显高于读取**。读取则可以通过只读副本就近完成。所以 D1 最适合**读多写少**的场景；全球高频写入的应用要谨慎。

### 2. 最终一致的读副本

开启读副本后，刚写入的数据立即从另一个副本读取，可能读到旧值。如果你的业务要求"写完立刻能读到"（read-your-writes），需要在会话内保持读主库，或者用 D1 提供的 bookmark 机制约束读取的一致性边界。对于统计、列表这类场景，秒级延迟通常无所谓。

### 3. 没有传统多语句事务

D1 不支持跨请求的交互式事务（`BEGIN`/`COMMIT` 这种会话状态没法在 Serverless 模型里保持）。替代方案是 `batch()`：一组语句按顺序执行，要么全部提交、要么全部回滚——这正是大多数"事务"需求的本质：

```typescript
await env.DB.batch([
  env.DB.prepare('UPDATE accounts SET balance = balance - ? WHERE id = ?').bind(100, 1),
  env.DB.prepare('UPDATE accounts SET balance = balance + ? WHERE id = ?').bind(100, 2),
]);
```

### 4. 限制要心里有数

数据库大小、单查询时长、每行/每结果集的大小都有上限（免费档和付费档不同，以官方文档为准）。GB 级以内的结构化数据完全够用；需要存大文件就用 R2，D1 里只存元数据。

### 5. D1 不是万能存储

一个简单的选型口诀：

- **关系数据、需要 SQL 查询** → D1；
- **键值缓存、配置、会话** → KV（全球强一致缓存，读取更快）；
- **大文件、图片、附件** → R2（零出口流量的对象存储）；
- **异步任务、削峰** → Queues + Consumer Worker。

真实项目里通常是几种组合着用，Worker 做统一入口。

## 九、总结

Workers + D1 的核心价值不在于某个单点技术多强，而在于**把"个人开发者维护一个后端"的成本压到了接近零**：

1. `npm create cloudflare` 建项目，`wrangler d1 create` 建库；
2. `wrangler.toml` 里声明绑定，代码里 `env.DB` 直接用；
3. SQL 迁移文件统一管理 schema，本地线上同一套命令；
4. prepared statement + bind 写查询，`batch()` 代替多语句事务；
5. `wrangler deploy` 上线，接进 CI 后彻底躺平。

对于读多写少、GB 级数据量的应用——博客、工具站、小型 SaaS——这套架构几乎没有对手。你的代码躺在全球 300 多个节点上，而你要操心的只剩下业务逻辑本身。
