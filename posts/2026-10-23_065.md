# WebAssembly：让浏览器长出第二台引擎，然后走出了浏览器

> 2017 年之前，浏览器里只有一门"真正能干活"的语言：JavaScript。想跑 3D 游戏、专业图像处理、视频剪辑，要么写成插件（Flash、NaCl），要么忍受 JS 的性能天花板。2017 年，四大浏览器在同一年支持了 WebAssembly（缩写 Wasm），浏览器从此有了第二台引擎：一种贴近机器的二进制指令格式，性能接近原生，沙箱依然安全。更有意思的是，它后来没有停在浏览器里——WASI 把它带上了服务端，Docker 联合创始人甚至说"如果 2008 年就有 WASM，就不会需要造 Docker"。这篇文章从它是什么、怎么工作、怎么编译、谁在用，一路讲到它走出浏览器之后的故事。

## 一、Wasm 是什么：二进制指令格式，不是新语言

先纠正一个常见误解：WebAssembly 不是一门编程语言，你不会"用 Wasm 写代码"。它是一种**可移植的二进制指令格式**——一套定义清晰的虚拟指令集，跑在所有主流浏览器共同实现的**栈式虚拟机**上。你可以把 C、C++、Rust、Go 等语言编译成这种格式，让它跑在任何实现了 Wasm 虚拟机的地方。

三句话概括它的定位：

1. **性能**：二进制格式比 JS 文本紧凑得多，解码远快于解析，执行性能接近原生（视负载不同，通常在原生的 50%–100% 之间）；
2. **安全**：跑在沙箱里，默认没有任何系统能力——不能读文件、不能开网络、碰不到内存之外的一寸空间，所有能力都要由宿主显式注入；
3. **互补**：它不是来取代 JavaScript 的。DOM、事件、网络请求仍然是 JS 的地盘，Wasm 负责的是重计算内核。

### 1. 和 JavaScript 执行管线的区别

JS 的问题不是"慢"，而是"不确定"：引擎拿到源码，先解析成 AST 和字节码，再用 JIT 一层层预热优化；一旦推测失误（比如类型变了），就要去优化（deoptimize）回退重来。Wasm 模块拿到手时已经是**提前编译好的二进制**，引擎只需要解码（decode）再编译成机器码——没有 AST，没有动态类型推测，启动路径短得多。主流引擎还支持流式编译（streaming compilation），可以边下载边编译，模块下完基本就能跑。

![JavaScript 与 WebAssembly 执行管线对比](images/post-065/wasm-pipeline.svg)

两者跑在同一个浏览器引擎里（V8、SpiderMonkey 既实现 JS，也实现 Wasm），共享进程和沙箱边界，这也是后面"互操作"的基础。

### 2. 标准化时间线

- 2015 年项目宣布，2017 年 Firefox、Chrome、Safari、Edge 全部支持 MVP（最小可用版本）；
- 2019 年 WebAssembly Core 1.0 成为 W3C 正式推荐标准；
- 此后能力持续补齐：128 位 SIMD 与线程（2021–2022 落地）、GC（2024 年进入正式标准）……

这个节奏值得记住：Wasm 的 MVP 很克制——先做好"重计算"这一件事，再花五六年补齐其余能力。后面会看到，GC 的落地直接改变了哪些语言能舒服地编译过来。

## 二、它怎么工作：模块、实例和线性内存

### 1. 三个核心概念

- **模块（Module）**：编译好的 `.wasm` 二进制，无状态的"可执行文件"，可以缓存（比如存进 IndexedDB）、共享、多次实例化；
- **实例（Instance）**：模块 + 一组导入（imports）跑起来之后的对象，携带可导出的函数、表和内存；
- **线性内存（Linear Memory）**：实例唯一能触碰的一块**连续、可增长**的内存，在 JS 侧就是一个 `ArrayBuffer`。

JS 侧加载并调用的最小示例：

```js
const res = await fetch('math.wasm');
const { instance } = await WebAssembly.instantiateStreaming(res, {});

// 调用模块导出的 add(1, 2)
const result = instance.exports.add(1, 2); // 3
```

### 2. 与 JS 的互操作：胶水代码与调用边界

Wasm 模块通过**导入/导出**与宿主交互：

- **导出（exports）**：Wasm 暴露给宿主的函数、内存、表；
- **导入（imports）**：Wasm 需要宿主提供的对象——DOM 操作、`Math` 函数、甚至另一个 Wasm 模块。

类型系统是 MVP 的一大约束：模块边界上只能传 **i32 / i64 / f32 / f64** 这几种数值类型和引用。字符串、对象、结构体都传不过去，只能放进线性内存，靠两端约定的内存布局共享。所以几乎所有 Wasm 应用都带一层"胶水代码"（Emscripten 生成的 JS、Rust 的 wasm-bindgen），负责在 JS 对象和线性内存之间搬运数据。

这也解释了一个反直觉的现象：**单个 Wasm 函数很快，但频繁跨 JS/Wasm 边界调用反而慢**——每次跨界都要做类型转换和数据搬运。正确姿势是"粗粒度调用"：把一整块计算（渲染一帧、解码一段视频）整体丢进 Wasm 做完再回来，而不是让 JS 和 Wasm 高频细粒度地互相调用。

## 三、怎么把代码编译成 Wasm

### 1. 先看一眼 WAT

Wasm 二进制对应的文本格式叫 WAT（WebAssembly Text Format），是人类可读的"汇编"：

```wat
(module
  ;; 导出一个 add(i32, i32) -> i32
  (func (export "add") (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add))
```

栈式虚拟机的风格一目了然：`local.get` 把参数压栈，`i32.add` 弹出两个操作数相加、再把结果压回去。实际项目不会手写 WAT，但读得懂它对调试很有帮助——浏览器 DevTools 里可以直接查看模块反汇编出的 WAT。

### 2. 主流工具链

| 源语言 | 工具链 | 说明 |
| --- | --- | --- |
| C / C++ | Emscripten | 最老牌、兼容性最好，自带 libc 移植层和文件系统模拟 |
| Rust | wasm-pack + wasm-bindgen | 体验最好的一档，自动生成 JS 胶水，支持直接导出字符串和结构体 |
| TypeScript 风格 | AssemblyScript | 语法接近 TS，前端团队上手最快，适合小到中型计算模块 |
| Go | 标准库 / TinyGo | 标准库支持 `js/wasm` 与 `wasip1` 两个目标；TinyGo 产物体积小得多 |
| Java / Kotlin | WasmGC | 2024 年 GC 标准落地后的新路线，Kotlin/Wasm 已随 Compose Multiplatform 可用 |

以 Rust 为例，完整流程就两条命令：

```bash
cargo install wasm-pack
wasm-pack build --target web
```

之后在 JS 侧直接 `import` 生成的胶水模块就能调用 Rust 函数。Rust 目前是浏览器端 Wasm 的一等公民：没有 GC 拖累、体积可控、工具链生态成熟。

## 四、它在哪儿被用起来了

技术讲再多，不如看几个真实产品：

- **Figma**：核心渲染引擎是 C++，编译成 Wasm。官方 2017 年给出的数据是加载时间缩短到原来的约 1/3；多人协同编辑器的重计算全在 Wasm 里，JS 只负责 UI 和调度。
- **Photoshop Web 版**：Adobe 2021 年把整个 Photoshop（数千万行 C++）用 Emscripten 编译进浏览器，配合 WebGL/WebGPU 渲染。这在 2017 年之前是不可想象的产品形态。
- **Google Earth**：最早依赖 Chrome 专属的 Native Client 插件，2020 年迁移到 WebAssembly 之后才覆盖全部浏览器。
- **游戏与模拟器**：Unity、Unreal、Godot 都支持把游戏导出为 Wasm 跑在浏览器里；DOSBox、MAME 等模拟器也因此变成网页版，老游戏重新"复活"。
- **媒体与工具**：`ffmpeg.wasm` 让视频转码直接在浏览器完成、文件不出本机；Google 的 Squoosh 用 Wasm 集成了十几种图像编解码器。
- **语言运行时**：CPython 编译成 Wasm 就是 Pyodide，JupyterLite 因此能把整套数据科学栈塞进浏览器标签页；SQLite 官方也提供了 Wasm 构建，数据库可以直接跑在前端。

这些案例的共同点很清晰：**核心逻辑是现成的 C/C++/Rust 资产，或者计算密集到 JS 扛不住**。这也是判断"该不该上 Wasm"最实用的两条标准。

## 五、走出浏览器：WASI 与服务端

### 1. WASI：给沙箱一个标准的"系统接口"

浏览器里的 Wasm 没有文件、时钟、网络——这对沙箱是优点，对服务端是缺陷。2019 年 Mozilla 发起 WASI（WebAssembly System Interface）：一组标准化的系统能力接口，让 Wasm 在非浏览器环境里通过"能力注入"拿到受限的文件、网络、时钟等能力。

关键设计是**能力即参数**：运行时启动模块时显式传入"你能访问哪个目录、能不能开网络"，默认什么都没有。传统容器是"给一个完整 Linux，再用权限和 namespace 圈起来"；Wasm 是"什么都不给，需要什么给什么"。两者的安全模型从根上就不同。

2024 年，基于组件模型（Component Model）的 WASI 0.2 落地：跨语言互操作从"只能传 i32"进化到"传组件接口"，字符串、列表、资源句柄都能在组件边界上直接表达。这是近几年 Wasm 生态最重要的基础设施进展。

### 2. "如果 2008 年就有 WASM"

Docker 联合创始人 Solomon Hykes 2019 年发过一条著名推文：

> If WASM+WASI existed in 2008, we wouldn't have needed to create Docker. That's how important it is. Server-side WebAssembly is the future of computing.

——如果 WASM 和 WASI 在 2008 年就存在，我们根本不需要发明 Docker。这就是它的重要性：服务端 WebAssembly 是计算的未来。

Docker 后来确实跟进：Docker Desktop 已经集成了 Wasm 运行时，可以把 Wasm 模块当作一种轻量"容器"来跑。对比传统容器，Wasm 模块的卖点非常直接：

| 维度 | 传统容器 | Wasm 模块 |
| --- | --- | --- |
| 冷启动 | 秒级（拉镜像 + 启动进程） | 毫秒级以内 |
| 内存占用 | 以百 MB 计 | 以 KB–MB 计 |
| 产物体积 | 几十到几百 MB | 常常只有 1/10 甚至更小 |
| 默认权限 | 一个完整的 Linux 环境 | 零权限，能力显式注入 |

### 3. 谁在生产环境用它

- **Cloudflare Workers**：2018 年起支持 Wasm 模块，JS/TS 与 Wasm 混合部署在同一 Worker 里；
- **Fastly Compute**：边缘计算平台，早期用自研的 Lucet 编译器，后转向 Wasmtime；
- **Shopify Functions**：商家用 Rust 写自定义逻辑编译成 Wasm，跑在 Shopify 的沙箱里——结账路径毫秒级冷启动是硬需求；
- **Envoy / Istio**：通过 Proxy-Wasm 标准用 Wasm 写代理扩展，逐步取代 Lua 插件；
- **wasmtime / wasmer / wasmCloud / Spin**：开源社区的服务端运行时与编排框架。

客观地说，服务端 Wasm 至今仍是一个增长中的生态，还没有动摇容器的统治地位。但"毫秒级冷启动 + 默认零权限 + 单一二进制产物"这三件事，恰好都打在容器最疼的地方。

## 六、局限与冷静看待

### 1. DOM 还是 JS 的地盘

Wasm 不能直接操作 DOM，所有 UI 操作都要经过 JS 胶水。对重计算应用（渲染引擎、编解码器）来说无所谓；对普通的增删改查页面，引入 Wasm 只是徒增复杂度。

### 2. 性能不是免费的

- 跨 JS/Wasm 边界的调用和数据搬运有实际开销，粗粒度设计是前提；
- GC 类语言（Java、Python）编译成 Wasm 往往是把整个运行时搬进去，产物动辄十几 MB；
- MVP 的 32 位线性内存上限 4GB，64 位（memory64）等提案仍在推进。

### 3. 调试与生态

二进制格式让传统调试体验打了折扣——好在 source maps 和 DWARF 调试信息的支持在持续改善，浏览器里也能直接看 WAT。生态里成熟的文档和排查经验仍集中在头部工具链（Emscripten、wasm-pack）上，选型前先确认你的语言和框架在目标平台上真的可用。

一个简单的判断清单，什么时候该考虑 Wasm：

- 已有 C/C++/Rust 资产要跑进浏览器（移植旧引擎、老代码）；
- 计算热点被 JS 卡住（解码、渲染、模拟器、密码学运算）；
- 解析不可信输入（文件格式解析）想放进沙箱，崩了也只是沙箱崩；
- 同一份核心逻辑要跨端复用（浏览器 + 服务端 + 插件沙箱）。

反之，普通表单页、内容页、增删改查——老实用 JavaScript 就好。

## 七、总结

1. WebAssembly 是一种可移植的二进制指令格式和沙箱虚拟机，不是一门要你直接写的语言；
2. 浏览器里它与 JS 互补：JS 管 DOM 和调度，Wasm 管重计算，记住"粗粒度调用"原则；
3. 工具链按源语言选：C/C++ 用 Emscripten，Rust 用 wasm-pack，TS 风格用 AssemblyScript；
4. WASI 与组件模型把它带出了浏览器：毫秒级冷启动、默认零权限的沙箱正在服务端寻找自己的位置；
5. 它的故事从来不是"取代 JavaScript"，而是"让平台不再只有一种语言"——浏览器如此，服务端也一样。
