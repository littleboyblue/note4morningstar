# Infra 与 SGLang：大模型从「能跑」到「跑得起」的那一层

> 一个模型在 demo 里跑通，和在线上同时服务一万人，中间隔着的不是更强的模型，而是一层几乎看不见的工程。这层工程有个笼统的名字——Infra。这篇文章分两部分：先把 Infra 讲清楚，它到底在管什么、为什么 GPU 利用率总是上不去、推理为什么必须拆成两个阶段来看；再讲 SGLang 这个具体的引擎，它怎么把「前缀复用」这一件事，从一个 kernel 优化做成一棵树、做成三级缓存、做成集群级的路由。最后给一份「什么时候该用它、什么时候别急着用」的判断清单。

*说明：文中 SGLang 的机制、参数与数字，以 2026 年 11 月的官方文档、release notes 与公开博客为准。这个项目迭代极快，落地前请以你装的那一版 `python -m sglang.launch_server --help` 为准；引用到的性能数字都标了出处和口径，我没有在自有集群上复跑过全部 benchmark。*

## 一、Infra 到底在管什么

### 1. 它不生产模型能力，它定价

AI Infra 是「让模型从一堆权重文件，变成可计量、可计费、可运维的服务」所需要的一切：算力、网络、存储、调度、算子与编译、训练与推理系统、观测与成本治理。

它本身不产生智能。它决定的是：这份智能以什么价格、什么稳定性、什么规模交付出去。

所以看一个 Infra 做得好不好，看的不是「有多少张卡」，而是几个朴素的比值：

- **单位 token 成本**：每百万 token 多少钱，这是最终会出现在账单上的那个数字。
- **有效算力利用率**：真正推进计算的算力占买来的算力的比例。卡在等数据、等通信、等调度，都算浪费。
- **TTFT 与 TPOT**：首 token 要等多久、每个 token 之间隔多久。前者决定「感觉快不快」，后者决定「读起来顺不顺」。
- **故障恢复时间**：一张卡挂了，服务掉多少容量、多久补回来、会不会连带把整个 batch 拖死。

最常见的误区是把 Infra 等同于机房。机房只是最下面一层。真正拉开差距的常在中间两层——**同一批卡，推理引擎和 kernel 换一套实现，吞吐能差出好几倍**。这就是「买了卡」和「有了算力」之间的距离。

### 2. 三个绕不过去的物理约束

Infra 的所有工程手段，归根结底都在绕三堵墙：

**显存墙。** 权重、KV cache、激活值共享同一块 HBM。70B 模型 FP16 权重就要 140GB，还没算 KV；而 KV cache 随并发数、上下文长度线性增长。显存不够，要么降并发，要么降精度，要么把 KV 挪出去——没有第四种选择。

**通信墙。** 张量并行每层都要 all-reduce，专家并行每层都要 all-to-all。算力可以堆，带宽堆不上去就只能等。一张卡算 10 毫秒、通信等 15 毫秒，利用率就掉到 40%，这时候再买卡只会让等待更长。

**调度墙。** 训练任务要几百张卡连续跑几天，推理服务要应付分钟级的流量突变，两边的资源画像完全相反。放在同一个池子里，一侧空闲时另一侧用不上；拆成两个池子，两边都按峰值建设，成本翻倍。

### 3. 为什么推理比训练更难「摊平」

训练是批处理，吞吐优先，跑完就结束。推理是长驻服务，要在延迟、吞吐、成本三个方向上同时守住。

更麻烦的是，**推理其实是两种完全不同的负载，只是被硬塞进同一个循环里**：

| | Prefill（预填充） | Decode（解码） |
| --- | --- | --- |
| 干什么 | 一次性吃下整段 prompt，算出全部 KV | 每一步只处理 1 个新 token，但要读全部历史 KV |
| 瓶颈 | 算力（大矩阵乘） | 显存带宽（访存）+ KV 容量 |
| 算术强度 | 高：权重读一次，可以算上千个 token | 低：权重读一次，只算一个 token |
| 决定什么 | TTFT | TPOT、整体吞吐 |
| 资源画像 | 卡不用很多，但要算得快 | 卡要多、显存要大，且必须常驻 |

算术强度差一个量级，意味着**混在一个 batch 里跑，GPU 两头都吃不满**：算力富余时被访存拖住，访存富余时被算力拖住。想同时优化，唯一的办法是把两种负载分开——这就是后面要讲的 PD 分离。理解了这一点，才看得懂 SGLang 那一堆看起来很像「运维参数」的开关。

## 二、推理引擎：Infra 里最锋利的一层

### 1. 引擎负责的那份清单

一台机器上跑一个模型，听起来是一句 `model.generate()`。引擎要把这句话变成可服务的东西，中间得做完这些事：

- **请求调度**：谁先算、算多少、什么时候插队，连续批处理怎么组。
- **显存管理**：KV cache 怎么切块、怎么复用、满了淘汰谁。
- **并行切分**：TP / DP / EP / CP 怎么摆，通信和计算怎么重叠。
- **计算加速**：attention kernel、量化、CUDA Graph、投机解码。
- **接口与前后处理**：OpenAI 兼容 API、tokenize、流式输出、结构化约束。
- **可观测**：缓存命中率、队列长度、每阶段耗时、每卡负载。

这些事只要有一件做得平庸，前面所有优化都会被吃掉。也正因为如此，引擎是整个 Infra 里竞争最激烈、迭代最快的一层。

### 2. 四代演进，一条主线

| 阶段 | 代表 | 核心问题 | 关键手段 |
| --- | --- | --- | --- |
| 朴素推理 | `transformers.generate()` | 一次只能跑一个请求 | 无批处理，KV 反复重建 |
| 服务化 | TGI、vLLM 早期 | 并发下显存碎片化 | PagedAttention：把 KV 切块管理 |
| 前缀复用 | **SGLang**、vLLM 后续 | 大量请求共享同一段前缀，却各算一遍 | RadixAttention：把前缀做成树 |
| 集群化 | llm-d、AIBrix、SGLang Model Gateway | 单机再快，跨副本命中率也会被轮询打散 | 前缀感知路由、KV 事件、PD 分离 |

四代不是替代关系，而是层层叠加：今天你用 SGLang，底下仍然站在 PagedAttention 式的分页内存管理和 FlashAttention 式 kernel 之上。**真正被重新发明的是「内存怎么组织」和「请求怎么分发」这两件事。**

## 三、SGLang 是什么

### 1. 出身：从一个 DSL 长成了一个引擎

SGLang 的名字来自 **S**tructured **G**eneration **Lang**uage。2024 年 1 月开源，论文同年进了 NeurIPS，作者来自 LMSYS 与伯克利 Sky Computing Lab。它最初想解决的问题很具体：LLM 程序里到处都是「生成 → 分支 → 再生成 → 汇合」的结构，为什么每次都要从头算？

于是它做了两件事：

1. **一个前端语言**：用 `gen`、`select`、`fork`、`join` 这些原语把多轮调用、分支、约束解码写进一个程序，交给编译器优化。
2. **一个运行时**：负责批处理、KV 复用、调度，把程序真正跑快。

有意思的是，后来社区用脚投票，重心从「语言」偏到了「运行时」——大多数人今天用 SGLang，根本不写那个 DSL，只是把它当成一个 OpenAI 兼容的高性能服务端（`sglang.srt`）。**这是开源项目里常见的错位：你为 A 造了它，世界因为 B 需要它。**

一句话定位：**一个把前缀复用做到极致、并且愿意为 MoE、长上下文、Agent 这类新负载去改内核和调度的推理引擎。**

### 2. RadixAttention：把「前缀」做成树

这是 SGLang 的立身之本，也是理解它后面所有设计的前提。

普通的分页缓存按「块」存 KV，能不能命中，取决于块号能不能对上。RadixAttention 换了个数据结构：**把 token 序列组织成一棵基数树（radix tree），每个节点对应一段连续 token 的 KV，从根到叶的一条路径就是一个请求的前缀。**

好处立刻出现：

- **共享前缀天然复用。** 三个请求都带着同一段 8K 系统提示，这段 KV 在树上只有一个节点，只算一次。
- **不用按整块对齐。** 只要前缀逐 token 一致就能命中，不受分页边界限制，也不会因为「只差一个 token」就整块重算。
- **淘汰有结构。** 树节点带引用计数和最近访问时间，容量满时从叶子往回收，被多个请求引用的节点更晚被淘汰。

![RadixAttention：三条请求共享前 10K token，只有各自的尾巴需要新算](images/post-069/radix-attention.svg)

这套机制对**闲聊**收益一般（前缀短、轮次少），对**Agent** 却是量身定做：长系统提示 + 工具定义 + few-shot 示例 + 多轮历史，动辄几千上万 token 完全重合，真正新增的往往只有几百个 token 的尾巴。**首 token 延迟约等于「需要新算的 token 数 × prefill 单位耗时」，分子从一万掉到两百，TTFT 就跟着掉一到两个数量级。**

2026 年的版本里还加了一层细节：会话感知缓存（`--enable-session-radix-cache`）。客户端在每个请求上带同一个 `session_id`，请求结束后它用到的缓存会被登记为该会话「软引用」；回收时先动没人引用的，再动被引用的。注意这是**软保护不是内存钉住**——真到显存告急，被引用的 KV 照样会被清掉。这类设计很能说明工程现实：所有「保证」最后都要给 OOM 让路。

### 3. 调度：连续批处理 + 分块预填充

两个细节决定了它在真实流量下能不能稳住：

- **连续批处理（continuous batching）**：不等整个 batch 跑完才收新请求，谁先结束谁先走，空位立刻补上。长尾请求不会拖住整批。
- **分块预填充（chunked prefill）**：一个超长 prompt 不独占一整个 step，切成若干块和其他请求的 decode 混着跑。代价是单请求 TTFT 略升，换来的是整体尾延迟显著变好。

这两件事单独看都不新鲜，难的是和 RadixAttention 的树、分页的内存池、CUDA Graph 的固定形状咬合在一起。**推理引擎的护城河从来不是某个点子，而是几十个优化互相不打架。**

### 4. 并行、量化、投机：该有的都有

- **并行**：TP / DP / EP / CP 都支持。MoE 模型上 `--ep-size` + `--moe-a2a-backend deepep --deepep-mode low_latency` 是常见组合，把专家并行的 all-to-all 压到延迟敏感模式。
- **量化**：FP8、INT4 权重与 KV 量化，配合 `--mem-fraction-static` 控制给 KV 留多少显存。
- **投机解码**：EAGLE 系与 NEXTN（MTP）都在支持列表里，DeepSeek 类模型可以直接吃原生 MTP 头。
- **图捕获**：`--cuda-graph-bs` 指定要捕获的 batch size 列表，命中就省掉逐层 launch 开销，没命中就退回 eager。

## 四、把单机优化放大到集群

单机做到极致，也只是把一台机器榨干。真实服务里还有两个问题：**KV 放不下**，**请求被分错机器**。

### 1. HiCache：KV 的三级缓存

RadixAttention 把单机的显存用满了，但显存终究只有几十 GB。HiCache 在此之上加了两层：

- **L1：GPU 显存（HBM）**，速度最快，容量最小；
- **L2：主机内存（DRAM）**，`--hicache-ratio` 默认按 GPU 池的 2 倍开，容量到 TB 级；
- **L3：共享存储**，可以接 Mooncake、HF3FS、NIXL、AIBrix，也能用本地文件后端；这一层才有**跨副本共享**的可能，前提是所有实例指向同一个命名空间。

元数据仍然用树（HiRadixTree），只是每个节点额外记录「这段 KV 现在在哪几层、地址是什么」。于是「命中」变成一个多级查找问题：HBM 有没有 → 主机内存有没有 → L3 有没有 → 都没有才重算。

![集群视角：路由决定命中，PD 决定延迟，三级 KV 决定命中上限](images/post-069/cluster-serving.svg)

### 2. PD 分离：把两种负载分给两种机器

回到第一节那张表。既然 prefill 吃算力、decode 吃带宽，那就干脆分开放：

```bash
# Prefill 节点：只做预填充
python -m sglang.launch_server --model-path $MODEL --tp 8 \
  --disaggregation-mode prefill --port 30000

# Decode 节点：只做解码
python -m sglang.launch_server --model-path $MODEL --tp 8 \
  --disaggregation-mode decode --port 30001
```

中间那次 KV 传输是全部代价所在，一般走 RDMA / NIXL / Mooncake，国产卡上也有对应后端。好处是两侧可以独立配比、独立扩缩容：长 prompt 流量涨了就加 prefill，会话变多、输出变长就加 decode——**这是「按秒计费的弹性」和「按峰值买卡」之间最直接的差别**。

再进一步还有 **EPD 分离**：多模态请求里，视觉编码器（Encoder）和语言模型（Prefill / Decode）的耗时画像又不一样，图片多的场景下编码器很容易成为瓶颈。SGLang 把它也拆成独立服务（`--encoder-only` / `--language-only` + `--encoder-urls`），于是形成编码 / 预填充 / 解码三级。

### 3. 路由：命中率是「分发」的函数

这是最容易被忽略的一环。单机缓存命中率再高，如果前面挂着轮询负载均衡，相关请求会被打散到不同副本，每个副本都得从头算一遍。

SGLang Model Gateway（原 Router）就是解决这个的：它维护一份「哪个 worker 上大概有哪些前缀」的影子树，把请求往命中概率最高的那台送，同时盯着负载，超过阈值就退回最短队列。

| 策略 | 逻辑 | 适用 |
| --- | --- | --- |
| `cache_aware` | 前缀匹配优先，负载失衡兜底 | 大多数场景的默认选择 |
| `power_of_two` | 随机挑两个，取更闲的那个 | 纯负载均衡、前缀无关 |
| `bucket` | 按负载动态分桶 | 流量形态差异大 |
| `lmetric` | 新前缀所需 prefill 量 × 当前负载，取乘积最小 | 想少调阈值、让打分自己权衡 |

效果有多大？SGLang v0.4 的博客给过一组 8×A100 的对照：同样是长前缀分组负载，**关掉 cache-aware 是 82,665 token/s、命中率 20%，打开是 158,596 token/s、命中率 75%**——吞吐接近翻倍，而模型和硬件一动没动。llm-d 在 Llama 3.1 70B 上给出的数字是同量级：前缀感知路由相比轮询，吞吐 3 倍、TTFT 快一倍。

这也解释了一件反直觉的事：**在多副本部署里，「缓存命中率」主要是路由器的指标，不是引擎的指标。**

### 4. 再往上一层：Kubernetes 与 llm-d

引擎到这一层就到头了，再往上属于编排：谁扩缩容、谁做灰度、谁在节点挂掉时把流量摘走。llm-d（CNCF Sandbox 项目，Red Hat、Google Cloud、IBM Research、NVIDIA、CoreWeave 共同发起）是这条路上的代表，它把 SGLang 当成一等后端：

- 用 `InferencePool` 把一组 SGLang pod 组织成一个逻辑池，EPP 做端点选择；
- SGLang 通过 `--enable-kv-cache-events` 用 ZeroMQ 把 radix 树的插入与淘汰事件发出来，路由器据此维护全局 KV 索引；
- PD 分离、分级 KV、SLO 感知的流控与自动扩缩，都由这一层统一编排。

到这里，Infra 的全貌才闭合：**kernel 决定一张卡的上限，引擎决定一台机器的上限，路由与编排决定一个集群的上限。**

## 五、为什么 2026 年它在 MoE、RL、国产卡上特别能打

**MoE。** DeepSeek 系列把专家并行推到了主舞台，而 MoE 推理的老大难是 all-to-all：通信量大、对延迟敏感、还容易出现专家负载倾斜。SGLang 在这块的投入很重——低延迟 DeepEP 模式、专家并行负载均衡（EPLB）、DP attention、以及跨节点的 PD 组合配置。DeepSeek 在开源周披露的推理系统里就是「PD 分离 + 大规模 EP」的组合，社区随后把大量工程反馈回流到了 SGLang 与 vLLM 两个引擎上。**模型厂和引擎厂在这件事上是互相喂饭的关系。**

**强化学习。** RL 的 rollout 阶段本质是「高并发推理 + 频繁换权重」，和线上服务的要求完全不同：需要引擎能原地休眠、释放 KV、把权重换掉、再唤醒，而不能每次重启进程重抓 CUDA Graph。SGLang 为此提供了内存释放/恢复端点、权重热更新（refit）、以及可选的确定性推理（`--enable-deterministic-inference`）来消除训练与推理之间的数值错位。它的 Model Gateway 也被用在 GLM 系列的大规模 RL 训练里——**训练和推理的边界正在模糊，引擎得同时站两边。**

**国产卡。** 昇腾 NPU 上已经有成套的部署文档和 DeepSeek-V3.2 最佳实践配置，连 `--attention-backend`、chunked prefill 兼容性这些细节都列了表。这件事的意义不在「多支持一个硬件」，而在于**国产卡的软件栈最缺的就是这种被反复踩过的默认配置**。

## 六、六个坑，给准备上的人

1. **版本跑得比文档快。** 这个季度对的参数，下个季度可能改名或默认值变了。上线前锁版本号，升级前读 release note，别照着半年前的博客配生产。

2. **参数是生死线，不是微调。** `--mem-fraction-static` 开太高直接 OOM，开太低 KV 池太小、并发上不去；`--tp` 摆错会和 NVLink 拓扑打架；`--page-size` 和 HiCache 强相关；`--cuda-graph-bs` 漏了你实际用的 batch size，图捕获就白做。

3. **benchmark 是别人的 workload。** 输入/输出长度分布、前缀重叠度、并发曲线，三项里换一项结论就反过来。**先测你自己的流量，再看别人的数字。** 尤其是「缓存命中率 90%」这种指标，它衡量的从来不是引擎，而是你的业务有没有共享前缀。

4. **PD 分离不是免费的。** KV 要跨机搬一次，网络成为新的瓶颈点；组件多了一倍，故障面也跟着翻倍；prefill 与 decode 的配比要按流量算，配错了比不拆还慢。**单机还有余量的时候，先别拆。**

5. **命中率不是白给的。** 前缀缓存意味着「别人算过的 KV 可能被你再利用」，这本身不泄露内容，但会留下可观测的时序侧信道；多租户场景要确认隔离边界。另外，缓存频繁抖动（写满 → 淘汰 → 重算）比没有缓存更糟，容量要留余量。

6. **引擎不是全部。** 网关限流、超时重试、日志与追踪、GPU 故障自愈、模型热切换——这些都不在引擎里，但用户感受到的稳定性由它们决定。见过太多团队把引擎调到极致，最后被一个没有上限的重试打崩。

## 七、上手与选型

最小可用的一条命令：

```bash
pip install "sglang[all]"

python -m sglang.launch_server \
  --model-path Qwen/Qwen3-32B-Instruct \
  --tp 8 \
  --mem-fraction-static 0.85 \
  --enable-metrics \
  --port 30000
```

服务起来后就是 OpenAI 兼容接口（`/v1/chat/completions`），前端代码一行不用改。

按场景挑开关：

| 你的场景 | 先开这个 | 关键参数 |
| --- | --- | --- |
| 长系统提示 + 多轮 Agent | RadixAttention（默认开）+ 会话缓存 | `--enable-session-radix-cache` |
| 多副本、大量共享前缀 | HiCache + 前缀感知路由 | `--enable-hierarchical-cache --hicache-ratio 2`，路由 `--policy cache_aware` |
| 长 prompt、TTFT 是核心指标 | PD 分离 | `--disaggregation-mode prefill/decode` + 传输后端 |
| 单机 8 卡跑 DeepSeek 类 MoE | EP + 低延迟 all-to-all | `--ep-size 8 --moe-a2a-backend deepep --deepep-mode low_latency` |
| 多模态、图片多 | EPD 分离 | `--encoder-only` / `--language-only --encoder-urls` |
| RL rollout | 休眠唤醒 + 确定性推理 | `--enable-deterministic-inference` |
| 只是想省点钱 | 先做量化，再谈架构 | FP8 / INT4，配合 `--mem-fraction-static` |

一句建议：**先量命中率，再谈集群。** 如果你的流量几乎没有共享前缀，RadixAttention 帮不上忙，HiCache 也只是多占内存；反过来，如果命中率能到 70% 以上，再往 PD 分离和集群路由上投，收益才是叠加的。

## 八、结语

Infra 这层东西的特点是：**做好了没人夸，做砸了所有人都骂。** 模型发布会上的分数是显性的，而「同样的卡多服务三倍人」是隐性的——它不出现在任何榜单里，只出现在财务和告警里。

SGLang 值得单独拿出来讲，不是因为它某个 benchmark 数字最高，而是因为它把一个很朴素的洞察做穿了：**推理里大量重复计算是「前缀」造成的，而前缀是有结构的，有结构就能共享、能缓存、能分层、能路由。**

从一棵树（RadixAttention），到三层存储（HiCache），到两种角色分工（PD / EPD），再到一层路由（Model Gateway）——每一次放大都只是把同一个想法推到更大的作用域。这也是判断一个 Infra 团队水平的办法：**看它能不能说清楚自己的瓶颈在哪一层。** 说不清的，往往只是在换硬件。
