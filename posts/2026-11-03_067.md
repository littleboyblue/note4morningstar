# 从"用 Agent"到"管 Agent"：读 DeepSeek《Super-agent 设计探索》

> 10 月 31 日晚，DeepSeek Harness 团队在公众号发布了长文[《Super-agent 设计探索：迈向更自主的 Agent 系统》](https://mp.weixin.qq.com/s/zoS7GlReWPhfCjENGxXCdg)，同晚开源了研究原型 [dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)（MIT 协议）。没有新模型，没有新产品，讨论的是一件更底层的事：单任务 Agent 已经证明能干活，现在卡住生产力的是"人的注意力"。我读下来的整体感受是：这更像一份 Agent 操作系统的设计草案——把调度、缓存、存算分离、看门狗这些计算机系统的经典套路，完整地适配到了 LLM 的不确定性上。这篇笔记先还原它说了什么，再讲我读出来的几层意思。

## 一、先还原事实

文章开篇就把定位说得很清楚：

> 本文是一篇面向工程实践的架构思路探讨，并非对 DeepSeek Harness 现有产品功能的介绍。

但"探讨"之外有两个硬事实值得注意。第一，团队内部已经有基于 DeepSeek Harness 运行的 Super-agent 实例在持续工作：同一个开发任务可以在 IM 和 GitHub 之间连续推进；它还会观察公共群聊，在**无人 @ 的情况下主动定位根因并提交修复 PR**。第二，配套原型当天就以 MIT 协议开源了。

它要解决的问题也很具体。现有 Agent 以单个 Session 为基本单位，Session 之间彼此独立；人并行推进多项工作时，只能手动切换、自己记住每个会话的上下文。团队观察到的数字是：**一个人通常只能同时跟进 3 到 5 个活跃 Session**。于是文章给出了全篇最锋利的一句话：

> 单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

围绕这个判断，Super-agent 被定义为具备四个特征的"连续实体"：

- **连续**：用户可以在 IM、GitHub 评论等日常界面交互，感觉始终只有一个 Agent。原文的例子很生动：先在 IM 里定了方案 A，后来在 PR 评论里改成方案 B，它能理解并调整方向。
- **高效**：不用等上一条命令跑完就能接新指令，多个复杂任务并行推进。
- **主动**：持续观察环境事件，主动推进值得做的事，不需要介入时保持安静。
- **持久**：始终在线，直接接入真实工作环境，长期运行中遇到异常能自愈。

注意最后两个特征里的措辞：主动但"保持安静"，在线且"能自愈"。整篇文章的工程重心，其实都落在这些限定词上。

## 二、五个模块：把 Agent 系统当分布式系统来设计

![Super-agent 架构示意](images/post-067/superagent.svg)

原文用五个模块支撑四个特征，我按自己的理解重排一下。

### 1. 双层架构：Router 分派，Worker 干活

第一个模块解决"连续"与"高效"的根本矛盾。如果所有事件都进同一个 Session，上下文最连续，但一个 ReAct Loop 是串行的，吞吐上不去，多任务的中间细节还会互相污染；如果每条事件都新开 Session，吞吐最高，但任务之间的关联断了，多个会话各自回复用户也会造成混乱。

拆法是把"维护全局连续性"和"高并发执行"放到两层：

- **Router 层**常驻，承接所有入口的人类交互，是全局的"序点、协调点和记忆"。它不执行具体任务，甚至可以不配 Bash 工具；按原文的实践，Router 的任务常常没有想象中复杂，**用较轻量的模型就能兼顾速度与效果**。
- **Worker 层**由上下文隔离的执行会话组成，挂载完整工具，用最强模型专注完成单一任务。Worker 不直接与用户交互，只向 Router 汇报状态，由 Router 统一对外回复。

这看起来像常见的 Agent Team，但侧重点不同：Agent Team 的主会话要深入任务细节、高频协调子步骤，推理负载很重；Super-agent 的 Router 只处理**任务之间**的高层关联与分派。原文还补了一句很实在的话：如果通过提示词约束一个 Agent Team 的主会话不亲自执行、只负责对外交互和分派，那它也可以视为这种双层架构。换句话说，双层架构不是某个产品的专利，而是一种组织原则。

原文对 Session 的定位也值得抄下来：

> Session 应当是系统的实现细节，而不应是用户的认知负担。

这句话听上去像产品口号，其实是架构约束：一旦 Session 是系统内部实现，Router 就必须真的接管上下文管理，而不是把"记得住上下文"继续外包给用户。

### 2. 事件驱动：从"人喂提示词"到"环境喂事件"

主动性的前提是换掉驱动源。Super-agent 的主要输入不再是用户逐条敲的提示词，而是 **Trigger**：群聊消息、邮件与日程、代码审查评论、CI 运行结果。

真实环境的特点是"高噪音、低触发率"，所以事件进来先过两级过滤：程序层做快路径（来源、群组、白名单等确定性判断），模型层做慢路径（语义策略）。这借鉴的就是计算机系统里的 Fast Path / Slow Path。

过滤之后是路由。同一个 PR、同一个 IM 话题、同一封往来邮件下的连续事件构成一条 **Thread**；Router 只为 Thread 的初始事件创建 Worker，之后该 Worker 直接订阅 Thread，**后续事件由程序直通，不再经过 Router**。订阅是多对多的：多个 Worker 订阅同一条 Thread，就能看到彼此在同一个 PR 上的操作，自行发现和解决冲突，不需要点对点通信。

再往下是上下文组织，这部分是我认为全文最"工程"的段落：

- **Inline & Spill**：把上下文窗口当 Cache 管。先只给对象 ID 和摘要；利用局部性逐步内联（关联对象 ID、前后文、相邻评论）；超长内容截断，保留续读入口，需要时再调工具读。原文的说法是——**"浪费上下文窗口，就是浪费模型的智能。"**
- **链式召回（Chain of Recall）**：Trigger、Thread、Worker Session 都有唯一 ID，注入时内联下一跳的 ID，对象之间因此构成一张引用图；模型从当前事件出发，顺着引用关系逐跳召回旧任务的上下文。这是 Router 在长程运行中不丢记忆的关键。
- **投机执行**：在结果还不确定是否会被采用时，后台先干起来。群里有人反馈问题，Agent 先在后台复现、找修复方案，**只有确认找到简单修法才开口，否则全程安静**；个人助手场景则是先核对日程、备好回复草稿，等用户确认。

### 3. 面向人的交互：全双工，且按信道调整音量

经典的 ReAct Loop 里，一次同步的 `run()` 会把整个循环阻塞住，工具跑多久，会话就哑多久。Super-agent 把耗时工具改成异步的 `start()` / `stop()`：调用 `start()` 立刻返回"已启动"，后台跑完再把结果作为一条新事件投递回会话；模型也可以主动 `stop()` 掉跑太久的命令。这就是原文说的**异步 ReAct Loop**，也就是"全双工"交互。顺带一提：官方说这套异步任务机制**已经在 DeepSeek Harness 里实现，但尚未默认开启**。

另一个细节是输出密度。Worker 冗长的推理和密集的工具调用被隔离在内部，对外统一由 Router 说话，并按信道定制：IM 里"像人类同事一样"，只在需要决策或验收时发通知，**单次回复不超过 100 词**；GitHub、邮件则写完整的结构化说明（问题背景、改动说明、验证结果）。

### 4. 计算、状态与环境的分离：BYOM

"持久在线"靠的是把三样东西拆开：

- **计算**：推进 Agent Loop 的部分做成云端无状态容器，可水平扩展、重启、替换；
- **状态**：会话等需要持久化的信息存数据库；
- **环境**：代码仓库、本地工具链、私有凭据这些"重状态"留在原地，端侧只装一个不保存会话状态的轻量 daemon。

原文解释了为什么不在云端重建环境：真实工作环境里有未提交的本地修改、私有凭据、内网服务依赖、特定硬件和工具链，复制和同步的成本高还容易遗漏；而要求用户整体迁云，迁移成本又太高。所以干脆让环境不动，云端按需接入——也就是 **BYOM（Bring Your Own Machine）**。这个思路与 Anthropic 提出的"脑手分离（Decoupling the brain from the hands）"一致，区别在于场景：那篇讲的是托管服务和按需沙箱，这里首先接入的是用户日常使用、可能间歇在线的个人机器。

### 5. Watchdog：主系统之外的第二个大脑

只做进程存活探测是不够的。Agent 的典型故障不是进程崩溃，而是**陷入无效循环或者偏离目标**——进程活得好好的，活儿就是不动。所以团队在主系统之外挂了一个独立的 **Watchdog Session**，用定时消息驱动，构成外部控制回路：除了处理接口报错、状态恢复失败，还要由模型判断每个 Worker 有没有实质进展、方向有没有跑偏；发现问题就介入，遇到偶发故障就持续复查。

有意思的是，Watchdog 本身也是一个有完整工具能力的 Agent 会话，维护者可以用自然语言问它"为什么卡住了"，也可以让它在线修正主系统——改提示词、调整触发规则。

## 三、实验：三组数字，和它们没说的部分

官方强调实验基于合成负载与简化环境，只能作为初步参考。设置是这样的：群聊加 GitHub CI 消息流驱动，每次约 300 条消息，其中约 20 条是工作请求，其余是闲聊、跟进、叫停和 CI 消息；**编码工作用一个只消耗时间的工具代替**；每种方案跑 5 次。

| 方案 | 完成时间 P50 / P95（分钟） | 单次实验读缓存 token |
| --- | --- | --- |
| Super-agent | 12.4 / 15.7 | 2323 万 |
| Super-agent，去掉订阅直通 | 12.6 / 15.5 | 3177 万 |
| 单 Session + Subagent 工具，中性提示 | 20.4 / 29.5 | 605 万 |
| 单 Session + Subagent 工具，提示优先委派 | 13.8 / 29.0 | 1082 万 |

这张表信息量很大，至少能读出三件事。

**第一，让模型自己决定"分不分工"，不可靠。** 中性提示下，5 次运行里模型**一次都没有调用 Subagent**，所有活都在主 Session 里做，还不断被新消息打断，p95 冲到 29.5 分钟。换成"优先委派"的提示后，4/5 次委派了，p50 降到 13.8 分钟——但剩下 1 次模型判断"活儿很小"自己做了，p95 仍是 29.0 分钟。原文的结论很克制：与其依赖提示词工程和模型临场判断，不如在系统层面把"谁来干"固定下来。

**第二，双层架构买到的其实是尾部稳定性。** Super-agent 的 p50 只比最好的单 Session 方案快 1.4 分钟，但 p95 从 29.0 分钟砍到 15.7 分钟，p95 与 p50 的差距只有 3.3 分钟。对个人用户，1.4 分钟的均值提升几乎无感；对团队，尾部延迟决定"要不要人盯着"。这是我读这篇长文时最想强调的一点。

**第三，订阅直通省的不是时间，是 Router 的预算。** 去掉直通后完成时间基本不变（12.6 / 15.5），但 Router 要做的决定多了约 30%，读缓存 token 从 2323 万涨到 3177 万（+37%）。也就是说，直通是一个纯粹的"省注意力成本"的优化——它让常驻的全局节点少干重复的转发工作。

Router 层的批处理压测也值得记一笔：Trigger 到达速率从每分钟 1 条提到 40 条，平均 batch 从 1.0 涨到 2.8，单次请求耗时只从 2.5 秒到 3.9 秒，**单个决定分摊的推理时间反而从 6.4 秒降到 1.6 秒**。拥堵时合并处理，越堵越"划算"，这也是官方认为单个 Router 在团队规模下够用、不必过早水平切分的依据。

至于这张表没说的部分：编码工作被"只消耗时间的工具"替代，意味着它测的是调度与协作，不是写代码的质量；约 300 条消息、20 个请求的规模，也比真实团队小得多；token 成本的真实分布、单张工单要花多少钱，都还没有公开数据。把这些当作"方向验证"而不是"性能承诺"，是对这类文章比较合适的读法。

## 四、我的判断

### 1. 诊断比方案更值钱

整篇文章最有价值的不是某个模块，而是它把"人的注意力"写成了系统约束。一旦承认人只能跟进 3–5 个会话，目标函数就从"单任务更快"变成"人的吞吐更高"，后面的双层架构、订阅直通、输出密度限制，全都是这个约束下的自然推论。这和我在[《2026 年大模型与 Agent 工具演进盘点》](#post-064)里写的判断是一回事：今年的模型在往"长程任务稳定"上卷，而工具在往"标准化协作"上卷。

### 2. 这是一次"Agent 操作系统化"

把五个模块对号入座，会发现几乎每个设计都能在操作系统里找到原型：Router 是调度器，Worker 是进程，Thread 是文件描述符或会话句柄，订阅是事件分发，Inline & Spill 是页缓存，链式召回是指针追踪，投机执行是分支预测和预取，Watchdog 是看门狗定时器。原文自己也承认："我们并没有提出全新的理论，而是将计算机系统中经典的工程思想应用到了 Agent 系统的构建中。"

这话听起来像谦辞，其实是这篇长文最大的贡献：LLM 带来的不确定性——模型会跑偏、会陷入循环、会误判任务大小——并没有被"更强的模型"消解，而是被系统设计**隔离和兜底**了。提示词工程负责"让模型想对"，系统架构负责"让模型想错时也不出事"。这两件事的边界，被这篇文章画得比之前清楚。

### 3. 生产指标是尾部延迟，不是平均值

实验里最反直觉的一组数字是：p50 只快 1.4 分钟，p95 快一倍。放到真实场景里，这意味着什么？个人用 Agent，慢一点无所谓；团队把 Agent 放进值班表，最慢的那 5% 决定你要不要半夜爬起来看它。Agent 产品从 demo 走向"可运营"，分水岭就在这里——不是它平均多聪明，而是它最差的时候有多差。

### 4. "主动"的难点是克制

四个特征里，主动是最容易做成灾难的。原文对它的处理非常克制：开源原型里，主动发起的工作默认是 `observe` 模式——只记录"本来会做"，不执行；内部实例的"静默复现并修复"策略，也是确认找到简单修法才开口；IM 里单次回复硬性不超过 100 词。换句话说，这套系统把"什么时候闭嘴"当成一等公民来设计，把打扰当成一种成本来管理。

投机执行也是同一个思路：先在后台把活干了，验证有结果再交付，没结果就当没发生——**先验证再承诺**，把不确定性挡在用户之外。比起"能主动干活"，"知道什么时候不该说话"才是这类系统真正难的部分。

### 5. 3.8 倍的 token 是一张诚实的账单

Super-agent 的读缓存 token 是单 Session 中性方案的约 3.8 倍（2323 万 vs 605 万）。官方没有掩饰这一点，还给出了明确的权衡：用更多 token 换更短、更稳的完成时间。

这就引出一个很现实的问题：当 Agent 按 token 计费，"稳定性"是奢侈品。只有任务的价值密度足够高——修一个线上 bug、发一次版、盯一晚上的值班——多花的 token 才划算。我猜接下来一两年，"按任务、按结果计费"的讨论会越来越多，因为用户真正想买的不是 token，是"这件事被可靠地办完了"。

### 6. 原型的教训：先解决运维与安全，再谈智能

这点必须说清楚：官方自己讲原型"并非正式产品"，代码大量由 Agent 写成，文章里的一些设计也还没实现。原型开源后，社区很快给出了更接地气的反馈：安装链路脆弱（Node 24 下进程名变化导致 `status` 失灵、GitHub 通知权限配不对就静默不干活、版本对不齐就起不来）；[独立安全审计](https://www.ctfiot.com/314686.html)指出本机管理 API 的鉴权只依赖一个在部署文档里公开写明的请求头，被拒绝的消息还能在同一批次里"借用"白名单成员的授权；Worker 默认以 `danger-full-access` 运行，而订阅线程上的消息会作为上下文进入 Worker——公开仓库里任何能评论的人，都可能成为提示词注入的入口。

这些问题一点都不"AI"，全是经典的系统工程问题：权限、边界、可观测性、失败恢复。它们恰好说明，**"Agent 管 Agent"的第一道门槛不是智能，是运维和安全**。也正因如此，官方给出的默认值（observe 模式、白名单、不建议开自动合并）值得认真对待，第三方建议的"独立系统账号、先接私有仓库"也应该成为部署常识。

## 五、对行业和个人的启发

对工具厂商，信号很明确：单点能力——上下文长度、工具调用、代码生成——正在快速趋同，下一层护城河是调度、状态管理、权限模型和可观测性。谁先把"Agent 的 Kubernetes"做出来，谁就拿到了团队采购的入场券。

对团队，落地路径其实文章已经给了：先想清楚哪些工作**值得** Agent 主动做（而不是能做什么就做什么），用 observe 加白名单做低成本试点，把 Agent 当成新同事做 onboarding——最小权限、评审流程不变、结果可追溯。别一上来就接生产仓库，也别让它碰公开社区。

对个人开发者，我的建议是反过来的：别急着造 Super-agent。先把单 Session 的上下文工程、工具设计、结果验收做扎实；多 Agent 是放大器，它会把你的流程缺陷一起放大。你连一个会话都管不好的时候，管五个只会更乱。

最后留一句冷静的话。文章标题叫"迈向更自主的 Agent 系统"，但通篇最用力、写得最细的地方，全是**如何克制自主**：怎么过滤噪音、怎么限制输出、怎么默认不执行、怎么在系统外再挂一个看门狗。这可能是这一代 Agent 工程最诚实的注脚——自主不是放权，而是把信任边界设计得足够小。

## 六、总结

1. Super-agent 要解决的不是"Agent 会不会干活"，而是"人能不能管住多个 Agent"——3–5 个活跃会话就是当前的人体带宽上限；
2. 五个模块（双层架构、事件驱动、面向人的交互、存算与环境分离、Watchdog）本质上是把操作系统的经典套路搬进 Agent：调度、缓存、路由、守护、存算分离；
3. 官方实验的真正结论是**尾部稳定性**：p95 减半、均值只快 1.4 分钟，代价是约 3.8 倍 token；
4. "主动"的设计重点在克制：默认 observe、白名单、100 词上限、先验证再承诺；
5. 原型暴露的问题提醒我们，多 Agent 系统的第一道坎是权限、隔离、可观测性这些老问题——智能反而是最后才需要担心的那一个。
