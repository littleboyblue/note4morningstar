# 我的自托管清单：一台 N100 迷你主机，28 个服务，以及为什么不跑什么

> 一个人可以在自托管的世界里走多远？本文的主角给出了一种答案：一台 180 欧元买的 Beelink N100 迷你主机（16GB 内存 + 6TB 硬盘），上面跑着 28 个自托管服务——17 个原生进程加 11 个容器，全部由 systemd 管理，`htop` 显示内存占用约 7.5GB、CPU 在 30%–40% 之间波动。从换掉流媒体（Jellyfin）讲起，到照片（Immich）、监控摄像（Frigate）、密码（Vaultwarden）、任务（Vikunja）、智能家居（Home Assistant），再到他明确不碰的东西——*arr 栈、自托管邮件。选型口味非常鲜明：服务不暴露公网、原生运行优先、简单压倒一切。

*本文编译自 [What I Self-Host, What I Don't, and Why](https://viceconsole.fyi/blog/2026/10/10/what-i-self-host/)（viceconsole.fyi，2026 年 10 月 10 日发布），内容为原作者第一人称的中文整理，版权归原作者所有。*

## 一、从换掉流媒体开始

我一直有一只脚踩在自托管的世界里，远早于这个词流行起来。大学一年级，我就用床底下一台 Linux 主机跑网站——室友嫌风扇噪音把机器关了，网站就宕机。后来几年跑过 [MythTV](https://www.mythtv.org/)，再是 XBMC（也就是现在的 Kodi）。

最近几年我住在印度。按西方标准，那里的流媒体便宜得离谱：Netflix、Disney+（在印度叫 Hotstar）、Spotify 都订着。离开印度之后，我不愿意再付西方价格续订；但更让我受不了的是"参与度跑步机"（engagement treadmill）——尤其是对我的儿子。我们想把他的观看范围限制在某些节目里，但每个平台没完没了的"为你推荐"和"接下来看"不断制造冲突。虽然各家都有限制片单、关闭自动连播的选项，但要逐个服务配置、还得盯着客户端更新后重新配一遍——工作量实在太大。

于是我以另一种方式"掐线"（cut the cord）： ditch 掉流媒体服务，换成自托管的 [Jellyfin](https://jellyfin.org/)。

接下来的一年半里，Jellyfin 打开了通往更多自托管服务的大门：对云服务商的依赖一路降低，换来的是久违的稳定——不再被无谓的网站改版、价值存疑的新功能和一封封"服务条款更新、强制仲裁条款、数据泄露通知"的邮件轰炸。我自己读新版本的 release notes，自己决定要不要升级、什么时候升级。

## 二、几条基本原则

### 1. 任何服务都不暴露公网

除了跑在路由器上的 VPN 服务，**没有任何服务直接暴露在公网上**。不管多方便、应用号称多安全都不行——尤其在 AI 辅助破解的时代，我认为这么做根本不明智。

我的 ISP 对 IPv4 地址用的是 CGNAT（运营商级 NAT），所以家庭网络在 IPv4 上本来就无法从公网直达。VPN 服务只在 IPv6 上可路由——这个限制有代价，但对我的使用场景完全可行，顺带还挡掉了一批不友好的连接尝试。最大的代价是：**公共 Wi-Fi 几乎不提供 IPv6，所以 VPN 在外面基本连不上**。用手机时可以关掉 Wi-Fi 走移动数据……前提是那边有信号。

![家庭网络拓扑](images/post-066/homenet.svg)

### 2. 原生优先，复杂才容器化

能原生跑就原生跑，只有依赖复杂的才容器化。我热爱的形态是"**单个 Go 二进制**"；一个只提供 Docker Compose 文件、还要拉起 MySQL、Redis 加另外三个容器的服务？我已经在找替代品了。

依赖不压垮人的话，原生更快、更省资源，而且多个服务可以用同一套管理工具和命令。不用承受"得进这个容器才能跑命令、那个容器里没有 curl、还有个跑 busybox 参数全不一样、外加虚拟网络和端口映射"的心智负担。

### 3. 不再用 Docker

这不算什么原则性立场：我只是受够了在服务器上维护一套完全独立的服务管理体系。我本来就在用 systemd，而 [Podman 与 systemd 的集成](https://docs.podman.io/en/v5.0.1/markdown/podman-systemd.unit.5.html)如今已经非常成熟。需要容器的少数服务，用 Podman 跑、用 systemd 管，一套体系搞定。

## 三、硬件：一台 N100 迷你主机

去年我买了台 Beelink 迷你主机，具体型号是 S12 Pro：Intel N100 处理器、16GB 内存、512GB SSD。赶在"内存涨价潮"（rampocalypse）之前入手，只花了 180 欧元——同款在亚马逊现在的标价是 359 欧。疼。主机上另挂一块 6TB 硬盘存媒体。

我在 Hacker News 上[聊自己自托管了什么](https://news.ycombinator.com/item?id=49985548#50014938)之后，有人追问：这一切怎么可能在 16GB 内存上跑得动？答案是下面这些服务里有不少刻意降低资源占用的选择，但说到底：**跑一大堆东西，真的不需要多少硬件**。我显然不会在这台机器上跑本地 AI 推理，但除 AI 之外的一切，要么开箱即用，要么改两行配置就好。

### 1. 媒体与音乐

**Jellyfin**（Podman）——一切的起点。对媒体组织方式很有主见，但总体好用。我只用它管电影、电视和家庭录像，其他功能（电子书、音乐、照片）没法评价。儿子如今还记得 Netflix，但已经对 Jellyfin 很满意；我则很喜欢它**没有自动连播、没有推荐流、不用划过一堆垃圾找想看的东西**。资源管理上我普遍偏好 720p 而不是 1080p 以上——有台 4K 电视，但屏幕不大，SD 和 HD 的差别我看得出来，720p 对几乎一切内容都够用；DVD 翻录出来更是只有 576p/480p。

**Audiobookshelf**（原生）——有声书和播客。有声书主要是给孩子设置的，章节处理做得非常好。播客以前用 PlayerFM、后来 Pocket Casts，现在除非出门连不上 VPN，都用它。

**ARM（Automatic Ripping Machine）**（Podman）——自动化翻录和转码 DVD（蓝光我不搞）。是的，2026 年了，我还在撕 DVD。别忘了我们已经"掐线"：它既是新内容（对我们而言）的入口，也是获取双语内容（英语和法语）的方式。

**Gonic**（原生）——Go 写的 Subsonic 兼容服务端。我很早以前买过永久 Subsonic 授权，但原项目已经古老，现代替代品更好。我跑了两个实例：一个给孩子的音乐，一个给大人的。

**MPD（Music Player Daemon）**（原生）——有些方案就是好用，好用到不需要改变，MPD 是其中之一：它已经存在 23 年了。手机听歌走 Gonic（出门也能经 VPN 从家里串流），但**全屋音响的播放靠 MPD 经 Snapcast 输出**。同样跑两个实例：一个放音乐，一个放播客。

**Snapcast**（原生）——全屋同步音频。可以理解为 Sonos，但没有昂贵的厂商锁定和计划性报废。配置挺复杂，但效果真的很好；和 MPD 一样值得单独写一篇文章。以后我打算再买几个设备专门当 Snapcast 接收端。

**Yubal**（Podman）——下载 YouTube Music 歌单的小 Web 应用，会把下载的音乐正确命名、整理、打标签。视频下载我一般用 yt-dlp，手机上看视频用 NewPipe。

### 2. 照片与备份

**Immich**（Podman）——Google Photos 的替代品。我烦透了 Google 在应用里不停推广付费存储：我自己能管好空间，妻子却总在爆满边缘。去年（v2 刚发布后）全家迁到 [Immich](https://immich.app/)——所有网络活动都发生在家里，**满屏照片的页面加载快得多**。相册和家人共享也摸索出了自己的方案。要做的还很多：重复照片一大堆，而且存储不再是问题之后，我删照片视频也不如以前勤快了。

**Backrest**（原生）——[Restic](https://restic.net/) 备份软件的 Web UI。备份很重要，对照片（Immich）尤其如此。Restic 的去重和压缩做得很好，Backrest 让保留策略的管理变得简单。备份失败的通知发到 Gotify。

**Syncthing**（原生）——照片备份策略的另一部分。我在 MacBook 上配置了单向（只接收）同步，Immich 里的所有照片最终都会落到 MacBook 的外置硬盘上。

### 3. 监控摄像

**Frigate**（Podman）——网络录像机（NVR）。我最早用的是 ZoneMinder（"因为我是某个年纪的人"），但它显然已经过了巅峰期；[Frigate](https://github.com/blakeblackshear/frigate) 则非常出色。我接了 8 个 IP 摄像头：识别进入车道的人和车，并与 Home Assistant 联动做自动化（比如后院检测到人，就打开摄像头的探照灯）。

所有摄像头都跑在**低于其标称的分辨率**上：主要为了避免 Wi-Fi 网络拥塞；大多数摄像头还支持更低分辨率的 RTSP 子流，Frigate 正是用它做人形和物体检测。低分辨率省下了视频处理的 CPU 和内存，也省下了录像的磁盘空间——看清脸足够了。另外我所在国家的法律禁止拍摄公共道路，所以摄像头也不对准远处。

### 4. 网络与系统基础

**Caddy**（原生）——Web 服务器加反向代理。早年我不理解反向代理的价值，以为本地域名甚至"IP + 端口"就够了；后来服务越加越多，还都开始要求 HTTPS。于是我注册了个域名，用 [Caddy](https://caddyserver.com/) 自动申请 Let's Encrypt 证书——现在几乎所有服务在局域网（或 VPN）内都能用**友好的子域名加 HTTPS** 访问。加一个新服务，只是改一行 Caddyfile 的事。

**Samba**（原生）——共享网络存储，向服务器拷文件、和妻子共享重要文档都靠它。有意思的是：一个 80 年代开发、总是和 Windows 联系在一起的协议，居然仍然是局域网跨平台文件共享的最佳选项。

**Cockpit**（原生）——基于 Web 的服务器管理控制台，用系统正常的认证方式。对我来说主要用途是：发现那些没配通知的服务悄悄挂掉了。

**Beszel**（原生）——简洁的监控面板，通过 agent（老派意义上的小后台服务）采集 CPU 负载、内存、磁盘、温度、电池等指标，帮我看住家里其他几台主机（几台树莓派，还有一个 Proxmox 集群——也许是未来一篇文章的主题）。

**Gotify**（原生）——Go 写的简单推送通知服务。很多自托管服务直接支持 Gotify 通知，或者一个自定义 HTTP POST 就能发。配合 Uptime Kuma，我用它接收：服务或设备掉线、孩子在 Jellyfin 上看了什么、Audiobookshelf 里有新播客……等等。

**Uptime Kuma**（Podman）——在妻子几次说"X 怎么坏了"并需要我手动重启服务之后，我意识到得有个东西盯着这些服务。它简单但功能够用：ping 设备确认在线、检查 Podman 容器状态、检查各服务的 HTTP 2XX 响应，甚至能解析 JSON 载荷提取细节做健康检查。挂了的东西在重试几次后发 Gotify 通知。

### 5. 个人效率

**Actual Budget**（Podman）——预算软件，有桌面客户端和 Web 应用，支持自定义报表和规则分类。我只用它管预算和支票/储蓄/信用卡账户；投资账户用的还是云服务（某天想搬回来……）。它支持从各家银行自动导入交易，但我不用：每月底手动下载上个月的流水（优先 OFX 格式，没有就 CSV）再导入。对我来说可行，因为我主要用它做支出记录，而不是"真正的"（actual）预算。

**PocketBase**（原生）——以前我用一个 SQLite 文件加 SQL Workbench/J 直接管理特殊账户（HSA、529 等）的交易和收据；但随着跨国、跨币种、跨保险系统地搬家，事情变复杂了，我还想让妻子也能录入交易。于是迁到 [PocketBase](https://pocketbase.io/)——**说到底它也只是一个 SQLite 文件**，但多了个好用的 Web 管理前端，被我"滥用"成通用 CRUD 界面：简单到妻子也会用，同时我还能对底层数据库文件跑任意查询。

**Vikunja**（Podman）——我用了约十年 Trello；今年早些时候 Trello 一次灾难性的多日宕机之后，我决定找自托管替代品。凡是要为两个用户拉起 PostgreSQL 或 MySQL 的方案一律排除——[Vikunja](https://vikunja.io/) 默认就用 SQLite（也可配置其他后端）。它不完美，Android 应用缺些功能，但对我够用。单二进制部署？正中下怀。

**Vaultwarden**（Podman）——Bitwarden 的自托管实现。我用 [KeePass](https://keepass.info/) 多年，一直没有好的同步方案，索性不在手机上登录网站；妻子用 LastPass，又出泄露事故、自动填充又不好使。把她迁到 KeePass 不现实，于是我选了 [Vaultwarden](https://github.com/dani-garcia/vaultwarden)：开源、API 与 Bitwarden 兼容、直接配官方客户端。Bitwarden 的浏览器扩展我不算喜欢，但大体能用；Android 应用够好，连着局域网时自动无缝同步，否则走 VPN 手动触发同步。我唯一的担心是 Bitwarden 终将对 Vaultwarden 不友好、破坏客户端兼容性——目前另一个兼容客户端 Keyguard 并不开源，走 freemium 模式。

**Readeck**（原生）——把读过、想确保以后还能访问的东西打标签存档。研究生时代我是 Zotero 重度用户，但已经多年没写过参考文献了。先试过 Wallabag，但付费墙内容存不下来——哪怕我在手机上明明登录着；Readeck 则能把我手机上正在看到的东西存进服务器。

**FreshRSS**（原生）——Web 版 RSS 阅读器。如今我基本只访问两个网站，所以用得不多；主要订阅了一些自托管服务的 GitHub releases，方便看看新版本的特性和修复。

**Homepage**（Podman）——某个时刻我意识到：跑的服务太多，需要再跑一个服务来管理它们。[Homepage](https://gethomepage.dev/) 就是答案：几乎我跑的每个服务都有对应的 widget，一眼总览全局，或者一键跳到某个服务的子域名。

**Forgejo**（原生）——Gitea 的 fork，单二进制部署。GitHub 的 uptime 如今是段子的素材库，而自己的 git remote 带来的速度也确实舒服。以后我会配上 CI/CD 和 runner——至少用来部署这个博客。

**Transmission**（原生）——这个不必解释了。

**slskd**（原生）——[IYKYK](https://github.com/slskd/slskd)（懂的自然懂）。

### 6. 智能家居

**Home Assistant**（Podman）——这个大概值得单独写一篇。它非常出色，我完全无法想象要在 Google Home、Amazon Alexa 或 Apple Home 这类专有生态里完成同样的事情。设备厂商开始向 Matter 这类协议标准化之后，局面确实变好了，但 Home Assistant 给你的控制力和灵活性仍然难以匹敌。代价是学习曲线陡峭；我还需要认真思考：万一服务器挂了，怎么在不牺牲家庭功能的前提下兜底。

## 五、不托管、试过又放弃的

**\*arr 栈（Sonarr、Radarr、Lidarr……）**——每次读安装教程，感觉都是一副资源密集、动辄坏掉的泥潭，这和我在自托管服务里寻找的东西正好相反。

**Collabora Online**——彻底离开 Google 当然美好，但 Google Docs 作为便捷的信息存储与共享方式确实难以撼动。我的折中：默认用本地 LibreOffice Writer 和 Calc，除非文档真的需要上云。既然已经有共享网络盘了，再跑一个 Web 版办公套件就没有意义。

**Firefly III**——用 Actual Budget 之前试过它，当时以为自己需要内置的多币种支持。结果它配置复杂：多个容器，还有一个专门用来导入数据的容器。Actual Budget 简单得多；外币账户我自己写了个小脚本做汇率换算，所以 Actual 里的一切都保持美元计价。

**Owntracks**——我喜欢 Google Maps Timeline，但 Google 把位置数据限制在单台设备之后，我想过自托管。[Owntracks](https://owntracks.org/) 的 Android 应用无论怎么调电池和位置设置，都无法稳定上报位置。这个赛道上的另一个选项 Dawarich 想要"至少"跑四个容器（PostgreSQL、Redis、Sidekiq、Web 应用）——对我来说，所需的资源和可能换来的价值不成正比。

**Music Assistant**——如果你还没有一套满意的音频方案，它也许适合你。但我已经有 Gonic、Snapcast 和 MPD 组成的稳定组合，而 Music Assistant 似乎想"拥有"一切——比如不停重新排列我的 Snapcast 设备分组。

**邮件**——自托管邮件是"工作量巨大、收益极小"的典型：我赌不起发不出或收不到邮件的后果。最终目标是把 Gmail 迁到某家付费服务商，而不是自己托管。

## 六、总结

清点一下：**17 个原生服务加 11 个 Podman 服务，全部由 systemd 管理**。`htop` 此刻显示内存占用约 7.5GB，CPU 在 30%–40% 之间波动——这台迷你主机还能跑很多。

在 AI 抢购潮把计算机硬件价格一路推高的当下，我希望我们会继续看到那些**把简单和效率放在第一位**的可自托管项目。这台 180 欧的小主机证明了一件事：对绝大多数非 AI 的个人服务来说，硬件早就不该是门槛，克制的设计才是关键。
